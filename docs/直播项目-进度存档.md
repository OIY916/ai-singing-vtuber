## 一、目标

在抖音开一个 AI 虚拟主播直播间：
- 观众发弹幕 → AI 回复（气泡 + 可选语音）
- 观众点歌 → RVC 翻唱 → 播放
- 观众说「放 X」 → 直接播网易云原曲
- 画面是蓝发鲸鱼娘（大肥鱼形象）

**用户明确的关键设定**：
- **口型不需要对上**（不需要精准 Live2D，用静态图/即梦视频都行）
- 即梦年会员可用，视频素材只需「会动」，不用它发声
- 音色模型是**买断制**，明确可商用
- 有打赏，属于商用场景
- **气泡是所有文字的统一出口**（不只是唱歌时）

### 跨天归零

`roll_over_if_new_day()`：日期变了就把「今日礼物/今日点歌/送礼人数」清零，
但**保留**累计观看/点赞/在线人数（那是直播间维度，不是「今日」维度）。

⚠️ 没有这个的话，服务连续跑过午夜，界面写着「今日」实际显示的是「开机以来」，
属于骗人。已用 `tools/test_day_rollover.py` 验证。

### 一个曾经骗人的地方（本轮修正）

原来界面「今日点歌」绑的是 `stats.songs`，那个数在 `play_worker` 里 +1，
意思是**唱完了几首**，不是**被点了几首**（翻唱失败、被顶掉都不该算已唱）。
已拆成两个独立计数：
- `live.gift_today` = 收到点歌请求次数（界面用这个）
- `stats.songs` = 实际唱完的曲数

### 问题 1d：放原曲会选到「女声翻唱版」而不是原唱（已修）

**现象**：观众说「放 十年」，本想听陈奕迅原唱，可能放出个女生版翻唱。

**根因**：`/raw`（放原曲）和 `/sing`（翻唱）共用同一个 `_pick_song`，
而它硬编码了「女声优先」——那是为 RVC 音色筛的（模型是女声，男声歌会失真）。
但**放原曲根本不经过 RVC**，观众要的就是原唱，这时候偏向女生版是错的。

**修复**：`_pick_song(..., prefer_gender=True)` 加开关，`/raw` 传 `False`。
- `/sing` → 保持女声优先（模型需要）
- `/raw`  → 关闭女声加分，原唱自然占优

**验证**（`tools/test_raw_pick.py`）：同一批候选里，
翻唱选《十年 (女生版)》- 白允y，放原曲选《十年》- 陈奕迅 ✅

### 问题 1e：点歌 / 放原曲 顺序不可控（已重构为统一队列）

**用户需求**：「聊天框的点歌先放到点歌队列中，唱（放）完了再看下一个就行」

**旧结构的真问题**（比"顺序"更严重）：
两条独立链路，**各自都调 `Mixer.play_music`**（覆盖式）：
```
SING_Q → sing_worker → PLAY_Q → play_worker  ─┐
RAW_Q  → raw_worker  ─────────────────────────┴→ 都往同一个 Mixer 写
```
- `raw_worker` 边下载边自己播，播的时候还**阻塞**
- 期间 `play_worker` 若也开播，两者**互相顶掉** → 顺序完全不可控
- 「放 X」会打断正在唱的翻唱，或者反过来被翻唱顶掉

**新结构：一个入口，一个出口**
```
JOB_Q（请求，FIFO，点歌和放曲混排）
   → prep_worker（按到达顺序准备：该翻唱就翻唱，该下载就下载）
   → PLAY_Q（已就绪，顺序 = 请求顺序）
   → play_worker（**唯一**播放者，一首一首来，播完才下一条）
```
- `sing_worker` + `raw_worker` 合并成 `prep_worker`
- 流水线仍保留：正在播 A 时，prep_worker 已经在准备 B
- 界面队列卡片会标「原曲 / 翻唱」和「待播 / 准备中」

**验证**（`tools/test_queue_order.py`）交替提交「点歌晴天 → 放十年 → 点歌小情歌」：
```
▶ 晴天 (女声版) - GYBeat   （翻唱）
▶ 十年 - 陈奕迅            （原曲）← 原唱，不是女声版
▶ 小情歌 - 姜眠            （翻唱）
✅ 严格按请求顺序播放，一首没丢
```

### 问题 1f：真实开播后暴露的 4 个问题（全部已修，2026-10-27 16:xx）

**① 在线人数一直显示「—」** ← 用户反馈
- 根因：代码读的是 `userCountStr`，但 douyinLive **根本不推这个字段**
- 实测真实字段（靠事件日志抓到）：
  ```
  [在线人数] total=6 totalUserStr=97 totalPvForAnchor=97
  ```
- 正确语义：`total` = 当前在线，`totalUserStr` = **累计观看**（只涨不跌）
- 修复：改读 `total`，并加 `online_known` 标志区分「0 人」和「没收到」
- 验证：界面显示 `在线 6 / 累计 7 / 点赞 3`，全部正确

**② 真实观众发弹幕，AI 完全不回复** ← 用户反馈「咋不理我」
- 根因：`reply_prob = 0.4`，**60% 的弹幕被静默丢弃**
- 真实场景：观众连说「你会唱歌吗」「哈喽呀」「咋不理我」，一条都没回
- 修复：`reply_prob` 改为 `1.0`（全回），防刷屏交给 `cooldown`
- 加了日志：`[AI回复]` / `[弹幕忽略]` / `[错误] LLM回复`，以后能直接看出为什么没回

**③ 气泡和语音不同步** ← 用户需求「语音和它的回复气泡一起出现」
- 旧逻辑：**先上气泡 → 再生成语音**，而 RVC 生成一句要 **3.6~4.2 秒**（日志实测），
  观众看到文字后要干等 4 秒才听到声音
- 修复：把气泡交给 `speak`，等语音**真正开始播的那一刻**由 `voice_worker` 上屏；
  气泡停留时长 = 语音真实时长
- 验证（`tools/test_bubble_sync.py`）：**时间差 -38ms**，基本同一时刻

**④ 本地曲库无上限，会吃满磁盘**
- 原来缓存只进不出。一首 ~5MB，一个月点 1000 首就是 5GB，最终翻唱/下载全失败
- 修复：`_cache_evict_if_needed()` 按**最久未使用（LRU）**淘汰，默认上限 3000MB，
  每次写完新歌自动检查
- 新增接口：`GET /cache/list`（列出曲库，按最近使用排序）、`GET /cache/evict`（手动清）、
  `POST /cache/warm`（预热常用歌）

### 关于「已唱过的歌存本地曲库」——其实早就有，只是没暴露出来

RVC 服务本来就有缓存（`cover_service/cache/`），key = md5(歌名+歌手+模型+半曲)，
命中就直接返回，**不重跑翻唱**。日志里 `翻唱完成 耗时=5.0s` 就是命中缓存
（没命中要 27~80 秒）。

本轮补的是「能用起来」的部分：能列出曲库、能控制容量、能预热。

**怎么看曲库**：
```powershell
# 列出（按最近使用排序，这就是观众爱点哪些歌）
curl http://127.0.0.1:8899/cache/list
# 占用
curl http://127.0.0.1:8899/cache/stats
```

### 问题 1g：观众点歌完全没生效 —— 单字歌名被拦掉（2026-10-27 17:xx 已修）

**现象**（真实开播时）：
```
[AI回复] 观众=xxx-t 原话="唱一首 谁"  回复=好嘞，谁这首安排上...
[AI回复] 观众=千秋不是宝 原话="放 谁"  回复=行，千秋不是宝点的，谁这就放...
```
点歌指令**被当成普通聊天丢给了 LLM**，`[点歌]` 事件一条都没有，观众等不到歌。

**根因**：`parse_song_request` / `parse_raw_request` 里有句
```python
if not (2 <= len(cand) <= 18):   # 歌名必须 ≥2 字
    continue
```
而观众点的恰好是**单字歌名**《谁》。实测网易云上确实有：
- 《谁》— 廖俊涛 / 张碧晨张靓颖版
- 《光》— 陈粒
- 《年》— 周菲戈

所以「≥2 字」这条把真歌也挡了。

**修复**：放宽到 `1 <= len(cand) <= 18`，同时把 STOP_WORDS 补严 ——
**只挡纯语气词/量词**（啊/呀/哦/嗯/哈/呢/嘛/啦…），
**绝不能挡实词**（谁/光/年/你/我 这类都可能是真歌名）。

**验证**：
```
唱一首 谁  → song='谁'      ✅ 会去翻唱
放 谁     → raw='谁'        ✅ 会放原曲
唱一首歌   → song=None       ✅ 仍被正确排除（"歌"是量词）
点歌呀    → song=None       ✅ 排除
唱得真好听 → song=None       ✅ 排除（夸赞不误判点歌）
```
真实测试「唱一首 谁」→ 65 秒后开始播放《谁 - 王贰浪》✅

### 问题 1h：错误日志没有堆栈，等于查不到（已修）

`log_error()` 原来只记「TypeError: can't multiply sequence by non-int of type 'float'」，
**没有行号**，翻遍代码也不知道是哪个 float 乘了字符串。

现在会把最后 4 层调用栈一起写进事件日志：
```
[错误] 位置=处理弹幕 原因=TypeError: can't multiply...
    ↳ main.py:1234 in handle_like
    ↳ main.py:590 in douyin_loop
```

**同时修了一个更严重的**：`handle_douyin` 抛异常会冒泡到外层 `except`，
导致**整个抖音 WS 断开重连**，那条正在处理的消息（可能就是点歌）直接丢失。
现在单条消息异常只记录不中断连接。

## 五、本轮修复的 Bug（重要）

### 问题 1：连唱第二首卡住 —— **已彻底修好（两个根因）**

**根因 A：mixer 音频回调尾帧广播异常（杀死整条输出流）**

现象（存档里一直挂着、未验证）：
```
[进度] 已唱 1 首 | mode=sing | 待播=1
最终: {'songs': 1}      ← 第二首没播
```

`stream/mixer.py` 的音频回调里：
```python
ramp = np.linspace(...)[:, None]        # 形状 (frames, 1) = (480,1)
out[:n] += self.music[...] * (ramp * gain)   # 但缓冲尾段是 (n,2)
```
播到**最后一帧**时 `n < frames`，numpy 广播失败：
```
ValueError: operands could not be broadcast together
            with shapes (353,2) (480,1)
```
这个异常发生在 **sounddevice 的音频回调线程**里 → 整条输出流静默停摆 →
`on_music_end` 永远不触发 → `play_worker` 永久卡在 `await done.wait()`。

修复三层：
1. `ramp[:n]` —— 切片对齐（`tools/test_mixer_tail.py` 覆盖 6 种长度全通过）
2. `_callback` 整体 try/except 兜底 —— 回调异常不再能杀死整条流
3. `wait_music_end()` 看门狗 —— 即使回调不来，也按「时长+15s」超时收尾

**根因 B：点歌在 wait 窗口里被 /speak 抢锁 → 歌被吃掉（真丢歌）**

修完 A 之后继续实测，发现「连点三首只唱了两首，第一首消失」。
日志抓到：
```
RVC /sing 失败: 503 {"ok":false,"error":"服务忙，正在处理另一首","keyword":"晴天"}
```

时序问题：`sing_worker` 取到队列项后，先 `await reply_to_bubble(...)` 安抚气泡，
**此时 `S.sing_busy` 还是 False**。弹幕回复的 `/speak` 就在这个窗口冲进去抢到了
GPU 锁，等气泡发完再调 `/sing` → 503，这首歌**永久丢失**
（`sing_worker` 里 503 被当成失败，`continue` 跳过，观众点的歌没了）。

修复三处：
1. **`speak()` 改判 `is_singing()`**（不再只看 `sing_busy`）——
   `is_singing()` 覆盖「SING_Q/PLAY_Q 非空 / 翻唱中 / 播放中」三阶段，
   只要「有关歌的事在流程里」就闭嘴，全部走气泡
2. **`S.sing_busy = True` 提到所有 await 之前**
3. **`rvc_sing()` 加 503 退避重试（3 次，2s/4s）** ——
   锁通常几百毫秒到几秒就放，重试基本都能拿到，绝不丢歌

**验证**：连点三首 → `songs` 依次 1→2→3，`play_q` 3→2→1→0，一首没丢 ✅

### 问题 1b：RVC 服务会自己死掉（实测抓到的真实现象）

排查过程中遇到「点歌后 5 秒就没了，没有任何翻唱记录」。
真相是 **RVC（8899）进程已经不在了**，主服务日志里全是：
```
RVC 异常: Cannot connect to host 127.0.0.1:8899 ssl:default [远程计算机拒绝网络连接。]
```
RVC 加载模型较慢（几十秒），如果在这期间被 `-Stop` 或重复启动打断，
就会留下一个「看起来起来了、其实已经死了」的状态。

**开播前必须确认**：`curl http://127.0.0.1:8899/health` 返回 200，
且 `Get-NetTCPConnection -LocalPort 8899` 有监听。`tools/prelive_check.py` 会查这项。

### 问题 1c：venv python 是「一对进程」不是重复实例（误判澄清）

排查时一度把两个 `python.exe` 都跑 `stream/main.py` 判成「重复实例」并误杀了正常服务。
真相：
```
astrbot-venv\Scripts\python.exe    ← 只是 launcher shim（26 万字节）
        └── Python310\python.exe   ← 它 spawn 出来的真解释器
```
这是**正常的一对**。判断是否真重复，要按「进程树根」去重（`Get-MainTrees`）。
启动脚本已改成按树根判断，并用 `taskkill /T` 连子进程一起结束。

### 问题 2：UI 数据缺失

原来 `/api/state` 只有 mode/stats/queue/clients。
本轮补齐：在线人数、累计观看、点赞、礼物收益、送礼人数、当前歌曲、
播放进度、音频电平、点歌队列明细。并新增 10Hz `panel` 推送（fetch 轮询做不到这个频率）。

### 问题 3：OBS 浏览器源尺寸不对

原来源是 **1080×1080 方形**，且被缩放到 307×307 摆在画面底部。
新 UI 是 1920×1080 的，方形源会把左右两栏直接切掉。
已用 `tools/fix_obs_source.py` 改成 **1920×1080 且铺满画布 (0,0) 1:1**，OBS 内实测渲染正确。

## 九、观众记忆库（2026-10-28 新增）

### 一句话

用 **`user.id`** 作为身份令牌，让 AI **记住每一个观众**：
他来过几次、点过什么歌、送过什么礼物，下次进来能说
「小明又来了啊，还想听之前你点的那首歌吗」。

### 为什么必须用 user.id 而不是昵称

| 场景 | 用昵称 | 用 user.id |
|---|---|---|
| 同一个人改了昵称 | 被当成新人，记忆全丢 | ✅ 还是同一个人 |
| 两个人都叫「小明」 | 记忆串在一起 | ✅ 是两个不同的人 |

实测确认 user 对象里字段齐全：
```json
{"id":"2973500164543661", "shortId":"4109237265",
 "secUid":"MS4wLjABAAAA...", "displayId":"fang49426",
 "nickname":"xxx-t", "webcastUid":"MS4wLjMJMJ4Il..."}
```
代码用 `id` 做键，`nickname` 只用于显示（每次消息都更新成最新昵称）。

### 存储

**SQLite 单文件**：`E:\qq-bot\data\memory.db`（WAL 模式，读写不互斥）

```
fans    id(PK) nickname first_seen last_seen visits
        gifts_value gifts_count songs_ordered msg_count
        summary summary_at
events  id fan_id kind content t weight
```

`kind`：`enter / chat / gift / song / raw / follow`
`weight`：送礼=3、点歌=3、放原曲=2、进场/聊天=1（检索时权重高的优先）

### 记忆内容（用户选的 A/C/D）

- **A 认识人**：来过几次、第一次/最近一次什么时候
- **C 偏好**：常点什么歌、送过什么礼物
- **D 亲密度**：互动次数、送礼总额

### 读取方式：检索 + 摘要（用户确认的方案）

**摘要**（长期稳定）
每人一段几十字的人物简介，由后台 `summary_loop()` 每 5 分钟挑几个人，
用他最近 20 条事件让 LLM 生成。存在 `fans.summary`。

**检索**（当下相关）
`recall(uid, keyword)` 按关键词捞相关事件；没命中就补最近的送礼/点歌。
礼品和点歌权重最高 —— 这样才能说出「之前你点的那首歌」。

**组合成注入文本** `profile_for_prompt()`：
```
关于小明：爱点周杰伦的歌，常送小礼物，是老粉
小明之前点歌：晴天；送礼：送了大啤酒×2；送礼：送了小心心×10
```
这段会拼进 LLM 的 system prompt，并附一句
「可以自然体现你记得他，但别生硬报数据、别每句都提」。

### 老粉欢迎（用户核心需求）

`welcome_returning()` 在**进场**时触发，但**刻意克制**，否则会变成刷屏机器人：

| 条件 | 说明 |
|---|---|
| 来过 ≥ 2 次 | 只欢迎回头客，新人说「又来了」很怪 |
| 距上次进场 > 30 分钟 | 刚出去又进来不算 |
| 90 秒内没欢迎过 | 防多次进出刷屏 |
| 且点过歌/送过礼/来过3次+ | 没互动过的路人不必招呼 |

满足后交给 LLM 生成欢迎词（带记忆），能说出「又来了啊，还想听之前那首吗」。

### 容量控制

`prune_events()` 每轮摘要后执行：
- 删掉 45 天前的**低权重**事件（chat/enter），送礼点歌保留
- 每人最多留 300 条（保留高权重和最近的）

### 控制台显示

控制台底部加了「🧠 记忆库」一行：记住多少观众、多少条、常客是谁。

### 测试

## 十六、大肥鱼爬屏特效（2026-10-28）

需求：让抠好的爬行立绘**贴着屏幕四条边爬**，爬到**天花板时有几率抓不住掉下来**。

### 文件

| 文件 | 作用 |
| --- | --- |
| `avatar/crawler/crawl.html` | 特效页本体（透明背景，直接给 OBS 浏览器源用） |
| `avatar/crawler/crawler_alpha.png` | 素材（头朝左的爬行姿势，透明 PNG） |
| `tools/obs_add_crawler.py` | 在 OBS 当前场景里建/删这个源 |
| `tools/record_crawl_demo.py` | 逐帧录制 → `crawl_demo.gif`（确认手感用） |
| `avatar/crawler/crawl_demo.gif` | 演示动图 |
| `avatar/crawler/crawl_storyboard.png` | 关键帧拼图 |

### OBS

```bash
python tools/obs_add_crawler.py          # 建源，默认隐藏
python tools/obs_add_crawler.py --on     # 建源并直接显示
python tools/obs_add_crawler.py --remove # 删掉
```

源名「大肥鱼爬屏」，画布尺寸，浏览器源 30fps，层级在皮套之上。
不传 `--on` 时是隐藏的，在 OBS 源列表点眼睛才出现，避免直播中突然冒出。

### 路径与朝向

底边 → 左边 → 顶边 → 右边 顺时针一圈（素材头朝左，所以底边是「向左爬」）：

| 边 | rotate | 朝向 |
| --- | --- | --- |
| 底边 | 0° | 正立，向左 |
| 左边 | 90° | 向上 |
| 顶边 | 180° | 倒挂，向右 |
| 右边 | 270° | 向下 |

四个拐角单独成段，位置和角度同时插值，看起来像翻过墙角。

### 可调参数（改 `CFG` 或 URL 上加）

`?h=0.16` 身高占屏比（1080p 下约 173px） · `?speed=115` 爬速 px/s · `?fall=0.10` 天花板每秒掉落概率
`?turn=0.55` 拐角转身耗时 · `?bg=1` 深色背景（仅预览） · `?hud=1` 状态角标

### 踩过的坑

1. **跨段按比例推进会瞬移**——拐角段只有 20px、直边段 348px，
   直接 `u -= 1` 带着余量跳段，等于把 20px 的进度当成 348px 的进度，
   角色一瞬间窜出去一大截。改成**按剩余时间**推进才正确。
2. **拐角不能按距离算时长**——20px 的拐角在 200px/s 下只有 0.1 秒，
   90° 转身会在一两帧内闪过去，看起来像穿模。拐角改用固定时长 `turnDur=0.55s`。
3. **`transform-origin` 要分清两层**——外层管位置+朝向（中心为轴），
   内层管起伏/摆动/落地压扁（脚底为轴），合成到一个 transform 里会互相干扰。
4. **落地压扁必须用脚底为原点**，否则会往地里陷。
5. **掉帧保护** `dt > 0.1` 要钳位，否则标签页切回来时角色直接飞出屏幕。
6. 录制演示 GIF 用「暂停 + 手动 `__crawl.step(dt)`」逐帧推进，
   截图耗时再长也不会让 GIF 忽快忽慢。

### 调试钩子

控制台可用：`__crawl.at('top')` 跳到某条边 · `__crawl.fall()` 强制掉落
`__crawl.pause(true)` 冻结 · `__crawl.step(1/15)` 手动推一帧 · `__crawl.state()` 看状态

## 十七、点歌队列持久化（2026-10-28）

### 问题

点歌队列 `JOB_Q` / `PLAY_Q` 原来**只在内存里**，主服务一重启就全空。
实际事故：直播中队列排了 18~20 首，为改配置重启一次，**丢了 3 首**（谁 / 夏天的风 / 小宇），
观众点的歌凭空消失。

### 方案

| 环节 | 实现 | 位置 |
| --- | --- | --- |
| 落盘 | `queue_save_loop` 每 2 秒检查一次，内容变了才原子写 `stream/queue_state.json` | `main.py` |
| 启动还原 | `_load_queue()` 把 `job`/`play`/`hold` 灌回内存 | `main.py` |
| 未开播暂存 | 恢复的歌标 `restored=True`，`play_worker` 不播而是放进 `S.restored_hold` | `main.py` |
| 开播放回 | `restored_flush_loop` 检测到 `live_state.online is True` 就把暂存放回 `PLAY_Q` | `main.py` |

`queue_state.json` 结构：

```json
{"job": [...], "play": [...], "hold": [...]}
```

- `job`：还没准备的请求（kind/name/kw），还原后由 `prep_worker` 重新翻唱
- `play`：已准备好的 mp3（**必须确认 mp3 文件还在**，`tempfile(delete=False)` 不自动删但可能被清理）
- `hold`：已还原但等开播的歌，**必须也在快照里**，否则再重启一次又丢

### 为什么不用「阻塞等开播」

第一版写成 `while not live: await sleep(2)`，结果：
1. 直接卡死 `play_worker`，整条播放链路停摆；
2. 被卡住的那首歌不在 `PLAY_Q` 里，**快照抓不到它**，再重启就真的丢了。

改成非阻塞暂存列表 `S.restored_hold` 才两边都对。

### 实测

- 写一份含 1 首 `play` 的 `queue_state.json` → 重启 → 日志出 `队列已恢复 1 首` ✅
- 该歌没有自动播（`stats.songs` 保持 0）✅
- `queue_state.json` 里出现 `"hold": [...]`，说明暂存也被持久化 ✅
- 开播后（`live_state.online=True`）暂存自动放回 `PLAY_Q` ✅

### 注意

- **重启丢歌问题从此解决**，但「正在播的那首」仍不会续播（从头开始），这是有意为之
- 队列变化频繁时每 2 秒写一次文件，开销可忽略（几 KB）
- 想看队列落盘情况：`cat stream/queue_state.json`

## 十八、弹幕回复「更像人」重做（2026-10-29）

### 用户需求

> 「我现在想要她能够更像人一样的回复弹幕」

### 问题诊断

改之前，弹幕回复是这样的（客服腔，一眼机器人）：

| 观众 | 旧回复 | 问题 |
| --- | --- | --- |
| 主播你好呀 | 你好呀，欢迎来到直播间～ | 空洞寒暄，没有对象 |
| 唱得真好听 | 谢谢你的支持！ | 标准客服话术 |
| 怎么不理我 | 抱歉让你久等了 | 道歉机器人，没有性格 |

根因是三个「看不见」：

1. **看不到直播间** —— `llm_reply` 只喂了人设 + 弹幕文本，模型不知道正在播什么歌、谁点的、有没有在唱歌、多少人看，只能凭空瞎聊。
2. **看不到对话** —— 历史里存的是**裸弹幕文本**（不带谁说的），多个观众混在一起，模型分不清谁说了什么，没法接话茬。
3. **没有性格** —— 人设就一句「活泼可爱的虚拟主播」，模型没有具体的说话方式约束，一律输出安全的礼貌腔。

### 修复（三件套）

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | 新增 `_live_context()`：把「正在播《X》(谁点的) / 有没有在唱 / 队列几首 / 大概几人」拼进提示词 | `main.py` |
| 2 | 重写说话规则：接话茬别另起话题、别复读、可以很短、带情绪性格（调侃/接梗/撒娇/得意）、拿不准就反问 | `llm_reply` 的 sys_prompt |
| 3 | 历史里保留「观众X说：」前缀，模型才能顺着话往下聊 | `llm_reply` 的 history 存储 |
| 4 | 人设换成有性格的大肥鱼（傲娇/爱撒娇/被夸会臭美/接梗/冷场主动找话题） | `config.json` 的 `persona` |

### 效果

| 观众 | 新回复 |
| --- | --- |
| 主播你好呀 | 小鱼干来啦！这名字一听就很好吃，我可不吃啊 |
| 你会唱周杰伦的歌吗 | 会啊，想听哪首？说慢了我就点别的了哦 |
| 唱得真好听 | 嘿嘿被你夸得有点飘了，等下跑调都怪你 |
| 怎么不理我 | 理你理你，刚忙着看弹幕呢，说吧想聊啥 |

### 可调的地方

- **人设性格**：`config.json` 的 `persona` 字段，想改傲娇/温柔/话痨直接改这里，不用动代码。
- **回复长度**：`max_chars`（默认 40）。
- **温度**：`llm_reply` 里的 `temperature`（0.9，越高越发散）。
- **对话记忆窗口**：`S.llm_history[-6:]`（6 条 ≈ 3 轮，多观众混在一起，太长会串味 + 费 token）。

**三层结构**：

| 层 | 频率 | 干什么 |
